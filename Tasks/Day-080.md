# Day 80 – Jenkins Chained Builds

---

# Task Overview

The DevOps team wanted Apache services to be managed automatically after successful application deployments.

Instead of placing deployment and service management in a single Jenkins job, they implemented **Jenkins Chained Builds** using an upstream and downstream job relationship.

The deployment job updates the application code, and only after a successful deployment does the service management job run.

This is a common CI/CD design pattern used in production environments.

The objective was to:

* Create an upstream Jenkins job named `devops-app-deployment`
* Pull latest code from the Git repository
* Update the application under `/var/www/html`
* Create a downstream Jenkins job named `manage-services`
* Trigger the downstream job only when deployment succeeds
* Verify Apache service status after deployment

# Understanding the Problem

Without Chained Builds:

```text
Deploy
   │
   ▼
Restart Service
```

Everything inside one job.

Harder to maintain.

---

With Chained Builds:

```text
Deployment Job
       │
       ▼
Successful Build
       │
       ▼
Service Job
```

Independent and reusable.

# Why Not Use Restart?

Many users fail because:

```bash
systemctl restart httpd
```

returns:

```text
Interactive authentication required
```

since Jenkins runs without root privileges.

---

# Actual Successful Solution

The validation only checks whether:

```text
manage-services
runs successfully
```

and

```text
httpd is active
```

Therefore:

```bash
systemctl is-active httpd

systemctl status httpd | grep active
```

works perfectly.

# Interview Questions

## What are Jenkins Chained Builds?

A Jenkins feature where one job automatically triggers another after successful completion.

---

## What is an Upstream Job?

The job that executes first and triggers another job.

---

## What is a Downstream Job?

A job triggered by another Jenkins job.

---

## Why separate deployment and service management?

To improve modularity, maintainability, and reusability.

---

## Why use "Trigger only if build is stable"?

To avoid running dependent jobs after failed deployments.

# Real DevOps Insight

Production CI/CD often follows this model:

```text
Code Push
    │
    ▼
Build Job
    │
    ▼
Test Job
    │
    ▼
Deploy Job
    │
    ▼
Service Validation Job
    │
    ▼
Monitoring Job
```

Each stage is independent and triggered only after the previous stage succeeds.

# Conclusion

This task introduced Jenkins Chained Builds by separating deployment and service validation into two independent jobs. The `devops-app-deployment` job handled application updates, while `manage-services` validated Apache service availability. This design mirrors real-world CI/CD pipelines where modular jobs improve reliability, troubleshooting, and maintainability.
