# Day 51 – Perform a Rolling Update in Kubernetes Deployment

---

# Task Overview

The Nautilus Application Development team released a new version of their Nginx application using the image `nginx:1.18`. The application was already running in the Kubernetes cluster through a Deployment named `nginx-deployment`.

The objective was to update the running application without downtime using Kubernetes Rolling Updates.

This task introduced one of the most important production deployment strategies in Kubernetes: **Rolling Updates**.

The objective was to:

* Identify the existing Deployment
* Update the container image
* Perform a Rolling Update
* Verify rollout progress
* Ensure all Pods are healthy after deployment

# Understanding the Problem

Before Update:

```text
Deployment
      │
      ▼
Pod 1 → nginx:latest
Pod 2 → nginx:latest
Pod 3 → nginx:latest
```

Goal:

```text
Deployment
      │
      ▼
Pod 1 → nginx:1.18
Pod 2 → nginx:1.18
Pod 3 → nginx:1.18
```

Without causing downtime.

---

# What is a Rolling Update?

A Rolling Update gradually replaces old Pods with new Pods.

Instead of:

```text
Stop Everything
      │
      ▼
Deploy New Version
```

Kubernetes performs:

```text
Old Pod Removed
      │
      ▼
New Pod Created
      │
      ▼
Repeat Until Complete
```

Users continue accessing the application during the update.

---

# Why Rolling Updates Matter?

Benefits:

* Zero downtime deployments
* Safer releases
* Automated rollout process
* Easy rollback support
* Production-ready deployments

---

# Kubernetes Deployment Lifecycle

```text
Deployment
      │
      ▼
ReplicaSet
      │
      ▼
Pods
```

During update:

```text
Old ReplicaSet
      │
      ▼
New ReplicaSet
      │
      ▼
New Pods
```

# Step-by-Step Implementation

## Step 1 – Connect to Jump Host

```bash
ssh thor@jump-host
```

### Explanation

Connects to the Kubernetes administration node.

---

# Step 2 – Verify Existing Deployment

```bash
kubectl get deployments
```

### Example Output

```text
NAME               READY
nginx-deployment   3/3
```

### Explanation

Confirms Deployment exists.

---

# Step 3 – Inspect Deployment

```bash
kubectl describe deployment nginx-deployment
```

### Explanation

Displays deployment details including container name.

---

# Step 4 – Identify Container Name

```bash
kubectl get deployment nginx-deployment -o yaml
```

### Explanation

Used when:

```bash
kubectl set image
```

fails because the wrong container name was provided.

Example:

```yaml
containers:
- name: nginx-container
```

Container name must match exactly.

---

# Step 5 – Update Image

If container name is:

```text
nginx-container
```

Run:

```bash
kubectl set image deployment/nginx-deployment \
nginx-container=nginx:1.18
```

### Explanation

Updates Deployment image.

---

# Rolling Update Process

```text
Old Pod
   │
   ▼
New Pod Created
   │
   ▼
Health Check
   │
   ▼
Old Pod Removed
```

Repeated until all Pods use the new image.

       ▼

       ▼

# Common Mistakes

## Mistake 1 – Wrong Container Name

Wrong:

```bash
kubectl set image deployment/nginx-deployment nginx=nginx:1.18
```

Error:

```text
unable to find container named "nginx"
```

Correct:

```bash
kubectl get deployment nginx-deployment -o yaml
```

Find actual container name first.

---

## Mistake 2 – Updating Wrong Deployment

Wrong:

```bash
kubectl set image deployment/nginx ...
```

Correct:

```bash
kubectl set image deployment/nginx-deployment ...
```

---

## Mistake 3 – Not Checking Rollout Status

Always verify:

```bash
kubectl rollout status deployment/nginx-deployment
```

---

## Mistake 4 – Forgetting Image Tag

Correct:

# Real DevOps Insight

Rolling Updates are the default deployment strategy in Kubernetes and are used heavily in production environments.

Traditional deployment:

```text
Stop Application
      │
      ▼
Deploy New Version
      │
      ▼
Start Application
```

Result:

```text
Downtime ❌
```

Rolling Update:

```text
Old Version
      │
      ▼
New Version
      │
      ▼
Zero Downtime ✅
```

This capability is one of the reasons Kubernetes became the industry standard for container orchestration.
